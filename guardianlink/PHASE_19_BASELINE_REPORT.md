# گزارش خط مبنا — فاز ۱۹

**موضوع:** کارایی، باتری، مقیاس‌پذیری و آزمون بار  
**وضعیت کلی شواهد:** `BLOCKED_BY_ENVIRONMENT`  
**وضعیت تغییر کد:** هیچ بهینه‌سازی فاز ۱۹ در کد محصول اعمال نشده است.

## دامنه و روش

ممیزی منبع پیش از هر تغییر انجام شد. مسیر مجاز فاز ۱۹ عبارت است از: `AUDIT → BASELINE → PROFILE → IDENTIFY BOTTLENECKS → OPTIMIZE → BUILD → LOAD TEST → STRESS TEST → RECOVERY TEST → RE-MEASURE → COMPARE → DOCUMENT`. اندازه‌گیری فقط به شواهد اجراشده اطلاق می‌شود؛ بررسی کد منبع، اندازه‌گیری کارایی محسوب نمی‌شود.

## خط مبنای Web ــ اندازه‌گیری واقعی

فرمان `npm ci --ignore-scripts && npm run build` در پوشه `web/` موفق شد. Vite 7.3.6، تعداد 90 ماژول را تبدیل کرد و build در 2.66 ثانیه به پایان رسید.

| CSS | 35.46 kB | 7.61 kB | اندازه artifact؛ نه زمان رندر |

## ملاحظات ممیزی منبع (اندازه‌گیری نیست)

- مسیرهای فهرست اعلان‌ها از pagination محدود استفاده می‌کنند؛ تاریخچه SOS به‌ازای هر دستگاه با limit محدود دریافت می‌شود؛ current/history موقعیت و رخدادها نیز حد دارند. این‌ها فقط مشاهده کد هستند، نه تأیید رفتار runtime یا کارایی.
- `LocationRepo.insertPoints` هر نقطه را در حلقه داخل transaction درج می‌کند؛ batch JDBC نیست. بدون latency و plan واقعی، bottleneck اثبات نشده و تغییر درج/ایندکس توجیه ندارد.
- صفحه Web مربوط به SOS فراخوانی history را جداگانه برای هر دستگاه و با `Promise.all` انجام می‌دهد؛ این الگوی fan-out می‌تواند با شمار دستگاه‌ها رشد کند. تعداد query/تأخیر واقعی معلوم نیست؛ در این فاز تغییر API/داده بدون آزمون سازگاری و DB انجام نشد.
- پاسخ فهرست دستگاه‌ها `deviceOut` را برای هر ردیف فراخوانی می‌کند و `refreshHealth` در آن مسیر اجرا می‌شود. احتمال هزینهٔ تکرارشونده از کد قابل بررسی است، اما تعداد query و اثر زمانی runtime اندازه‌گیری نشده است.
- صف آفلاین موقعیت در منبع سقف 240 نقطه دارد و برای dedupe/trim فهرست را پیمایش می‌کند؛ صف رخدادهای سیاست برنامه سقف 500 و رخدادهای Web safety سقف 100 دارد. این اعداد ظرفیت حافظه اعلام‌شده در کدند، نه آزمون اندازه/مصرف/سرعت.
- NetworkWatcher هنگام دسترس‌پذیر شدن شبکه یک sync زمان‌بندی می‌کند. این رفتار منبع است؛ نرخ واقعی، coalescing کارها، مصرف شبکه و اثر باتری اندازه‌گیری نشده‌اند.
- Web polling برای health/unread معمولاً 60 ثانیه و SOS فعال 30 ثانیه در منبع تعریف شده است. این پیکربندی اثبات‌کننده بار واقعی یا رفتار tabهای متعدد نیست.
- Migrationها و ایندکس‌های موجود قابل بازبینی ایستا هستند؛ هیچ `EXPLAIN (ANALYZE, BUFFERS)` یا آمار واقعی DB در دست نیست. ایندکس جدید افزوده نشد.

## بودجه‌های هدف موقت

این‌ها **اهداف پیشنهادی برای gate آزمون بعدی‌اند، نه نتایج یا تضمین ظرفیت**. باید روی staging و دستگاه/شبکه تعریف‌شده تأیید یا اصلاح شوند:

| حوزه | هدف پیشنهادی برای پذیرش |
|---|---|
| API خواندنی متعارف | p95 ≤ 500 ms و p99 ≤ 1,500 ms؛ خطای 5xx < 0.5% در بار نامی توافق‌شده |
| queryهای DB متعارف | p95 ≤ 100 ms؛ همراه با اندازه‌گیری انتظار pool و lock جداگانه |
| Web bundle اولیه | JS gzip ≤ 200 KiB؛ خروجی فعلی 116.14 kB ده‌دهی است و build tool واحد را `kB` گزارش می‌کند، بنابراین تبدیل و آستانه در CI باید صریح باشد |
| Web تجربه مرورگر | LCP p75 ≤ 2.5 s، INP p75 ≤ 200 ms، CLS ≤ 0.1 در پروفایل دستگاه/شبکه آزمایشی مستند |
| Android | cold start p95 ≤ 2.5 s در دستگاه مرجع مشخص؛ هیچ I/O شبکه/DB سنکرون روی main thread؛ معیار حافظه باید با مدل دستگاه/نسخه OS تثبیت شود |
| باتری/شبکه | بودجه عددی تا تعریف سناریوی opt-in مکان‌یابی، مدل دستگاه، مدت آزمایش و کنترل مصرف پایه **تعیین‌نشده**؛ معیار ایمنی ثابت: بدون مکان‌یابی پس‌زمینه خارج از قابلیت/مجوز فعال و بدون polling حلقه‌ای |
| مقیاس‌پذیری | هدف ظرفیت عددی تا مشخص شدن بار نامی، mix درخواست، اندازه خانواده و منابع staging `INSUFFICIENT_DATA` |

## تصمیم و اقدام بعدی

بهینه‌سازی حدسی یا تغییر DB انجام نشد: ابزار لازم برای سنجش bottleneck، ساخت/test مجدد و re-measure وجود نداشت و آزمون بار امن در staging ممکن نبود. برای ادامه، محیط staging غیرتولیدی با PostgreSQL، JDK 17، ابزار Android و دستگاه مرجع، مرورگر خودکار و داده مصنوعی غیرحساس فراهم شود؛ سپس ابتدا سنجه‌های ناقص baseline گرفته شوند. هیچ آزمون سنگین روی production اجرا نشود.
